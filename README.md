# XFed-IDS-ByzAgent

A federated intrusion detection system that checks whether its own explanations and its own participants can be trusted.

## The system in five stages

The project is one system, built as a VIT-AP capstone. It has five stages.
Stages 3 and 4 are separate experiments with separate evidence, and their
findings are reported separately below.

**1. Data.** The Distrinet CICIDS2017 V4 dataset (a corrected release of
CICIDS2017), cleaned from 2,099,976 raw flows to 1,913,502 and mapped into
8 attack families plus Benign. Families under a 1,000-flow floor
(Infiltration, Heartbleed) are kept in the data and reported per class, but
left out of the headline macro-F1. The split is one global, group-aware
75/25 train/test split made before any federated partitioning, so no feature
vector appears on both sides. Every cleaning decision and its row count is in
[`data/README.md`](data/README.md).

**2. Federated training.** Ten organizations (silos) train a shared MLP
detector with Flower, without sharing traffic. Data is split across silos by
a Dirichlet draw over labels at α ∈ {0.1, 0.5, 5.0} (severe, realistic and
near-IID heterogeneity) with seeds 42, 1337 and 2024, giving 9
configurations. Partitions are stored on disk as row-to-silo assignments
with a SHA256 manifest that is checked every time a silo is loaded. The
round used for every reported number is chosen on validation macro-F1, never
on the final round.

**3. Explanation check.** Do the silos' models flag attacks for the same
reasons? Each silo computes SHAP attributions locally against a fixed,
seeded background drawn from its own training rows; only top-k feature
rankings cross to the server. Agreement between each silo and the global
model is measured with Jaccard@10 and weighted Kendall's τ, compared across
α, against a chance level, and against a null control: how much rankings
differ between centralized models that differ only by random seed.

**4. Trust check (ByzAgent).** Is any organization poisoning the model? A
label-flipping attack is injected into chosen silos. Each round, five
per-silo behaviour statistics (update norm, two cosine similarities, local
training loss, validation accuracy) are given to a local LLM agent
(`llama3.1:8b-instruct-q4_K_M` through Ollama), which decides trust,
downweight or quarantine for each silo and writes a short rationale. The
agent is compared against Krum, Multi-Krum and coordinate-wise trimmed mean,
and its rationales are audited against the numbers it was given.

**5. Dashboard.** A FastAPI backend and a React + Recharts frontend show
live detection on streamed flows, per-alert SHAP explanations, and the
trust decisions together. The served model is `fedavg_a0.5_s42` at round 18.
One-sentence LLM summaries of alerts in the dashboard (length not enforced)
are generated by the same local LLM; they are a usability feature, not a research claim. A static
showcase site (`site/`) and an explainer film (`film/`) present the same
results to a general audience.

**Reading the explanation check.** Explanation agreement rises with α, and
at α=5.0 it sits well above both chance and the seed-noise floor. At α=0.1
the median Jaccard@10 (0.333) falls below the floor's lower bound, even
though FedAvg macro-F1 at that α is 0.516 ± 0.048. That below-floor result is
directional, not significant: the cluster-bootstrap interval at α=0.1
([0.250, 0.429]) overlaps the floor ([0.429, 0.484]).

**Reading the trust check.** Every attack tested is a worst-case adversary
with full knowledge of the federation's composition, not a realistic
attacker. Krum, Multi-Krum and trimmed mean were given the true number of
attackers as an oracle; ByzAgent was not. Multi-Krum's apparent recovery at
f=2 is a compositional artifact (it always drops the same large,
Benign-heavy silos), not attack mitigation. ByzAgent's result, in the
project's locked wording:

> Both effects are present. A real compositional confound saturates some
> silos' flag rates independent of any attack; real attack-responsive
> detection is also present and becomes visible where silos are not already
> saturated. Seed 42's apparent null was partly a ceiling artifact of that
> seed's unusually bimodal composition.

ByzAgent produces decisions plus a rationale of measured fidelity. Giving it
a rolling history of past rounds failed its pre-registered test.

### Test-set use

All model and round selection used validation data. Three early design choices
were recorded with test-set numbers as their justification: 3 local epochs,
FedProx μ=0.0005 and StandardScaler. Re-checked on validation, the same μ and
scaler are selected; for local epochs, validation also selects 3 epochs over 1
at α=0.5 in all three seeds (mean best-by-validation macro-F1 0.9425 vs
0.8602). Headline test metrics come from one evaluation of each run's
validation-selected checkpoint. The test set was also read, without informing
any later choice, in these ways: (a) legacy client-side per-round scoring in
35 runs, unread by any analysis; (b) round-20 scoring for an earlier
round-lottery comparison, since replaced by a validation-based one; (c) 14
fixed rows as SHAP explanation inputs; (d) display-only use: 514 extracted
rows, and the dashboard simulator before 2026-10-13 (not logged, no
aggregate); (e) centralized pilot and baseline runs (18) and XGBoost seeds (3)
scored on test during development; (f) one preregistered re-evaluation of a
single validation-selected configuration
([`docs/preregistration_accuracy.md`](docs/preregistration_accuracy.md)). Full
table: [`docs/test_set_exposure_audit.md`](docs/test_set_exposure_audit.md).

## How this differs from prior work

- Oki et al. (IEEE Networking Letters, 2024) showed that federated training
  reduces explanation distance in a distributed IDS. This project does not
  dispute that; it characterises where the reduction breaks down as client
  data becomes more heterogeneous.
- It adds a null control that, as far as we found, prior work in this space
  does not report: how much explanation rankings differ between centralized
  models that differ only by random seed. Without it, a reported difference
  cannot be told apart from seed noise. The protocol is written up so it can
  be applied to other federated systems
  ([`measurement_protocol.md`](docs/measurement_protocol.md)).
- Gholizade et al. (arXiv 2607.13045, June 2026 federated-XAI survey) name
  explanation consistency under non-IID data as an open challenge and note
  that there are no standard metrics for it.
- The trust check tests Krum and its variants with 10 clients and an oracle
  attacker count, and audits how often the agent's own explanations are
  accurate.
- The LLM explanation sentences in the dashboard are a usability feature, not
  a research claim.

We do not claim to be the first to measure explanation agreement in
federated IDS, and we do not claim the broad "federated learning + IDS +
explainability" combination as new; several 2025–2026 papers cover it.

## What we did not claim, and other limitations

The full lists are in
[results A, Limitations](docs/contribution_a_results.md#limitations) and
[results B §10](docs/contribution_b_results.md#10-limitations-stated-plainly).
The ones most likely to matter to a reader:

**Explanation check**

- The α=0.1 below-floor result is directional, not significant (intervals
  overlap, see above).
- The round lottery is real: validation macro-F1 can differ by up to 0.118
  (α=5.0, seed 42) between the best-by-validation round and the final round
  ([`round_lottery_val.csv`](results/federated/round_lottery_val.csv)), so
  every number uses validation-based round selection.
- Silo size is not independent of label skew under Dirichlet partitioning;
  it is largely determined by it, and size-controlled partitions were proven
  impossible with this partitioner. After conditioning on log(size), KL
  divergence from the global label distribution still predicts agreement
  (partial r = −0.57 at α=0.1, n=29; −0.82 / −0.87 for Jaccard@10 / τ at
  α=0.5, n=30). This is observational, reported as r and n only with no
  p-values. Label entropy was the pre-specified covariate, failed this
  conditioning, and KL was substituted afterwards.
- Round-wise agreement declines from round 5 to round 20 at α=0.1 and α=0.5
  while validation macro-F1 rises, and is flat at α=5.0. This is directional
  and was computed at reduced SHAP fidelity (`nsamples=1000`).
- The FedProx result holds at μ=0.0005 only, which was not swept: agreement
  improves with flat accuracy at α=0.5 across all 3 seeds, is inconclusive at
  α=0.1 (n=3), and shows no effect at α=5.0.
- Parity-monitor flags rely on averaging at least 3 explainer draws;
  single-draw flags were shown to be artifacts.
- SHAP's Monte Carlo sampling is unseeded, so each headline agreement number
  reflects one draw per (config, silo).
- The faithfulness check is a single-config spot-check (α=0.5, seed 42),
  not a gate. The instability floor rests on 3 seed pairs. Silos within one
  run share a training trajectory, so the effective sample size is closer to
  the 3 seeds than to the silo count.
- Even in the corrected dataset, 43,890 flows labelled Benign or PortScan
  are feature-identical to a flow of the other family once identifier
  columns are removed. They were dropped as label conflicts; this is a
  ceiling set by the 82-feature space, not by any model.

**Trust check**

- All attacks are worst-case, full-knowledge adversaries, and the classical
  baselines were given the true attacker count as an oracle. No result here
  describes a naturalistic attack.
- ByzAgent does not "explain its reasoning". It produces decisions plus a
  rationale of measured fidelity: ≈35–45% of its trend claims under rolling
  history contradicted the data it was given, and its citation error rate
  rose from 11.7% at seed 42 to 22.5% at seeds 1337/2024.
- LLM decisions are nondeterministic; decision stability is reported
  alongside them.
- `train_loss` is the only strong attack signal (33.8×–154.3×), and for a
  label-flipping attack an elevated loss is close to definitional. The
  geometry statistics are weak to null, and validation accuracy inverts
  (malicious clients score higher on the Benign-heavy validation set).
  33.8×–154.3× is a seed-42 effect-size ratio, not a per-round detection
  threshold; a per-round train_loss threshold chosen on seed 42 did not
  transfer (seed 1337 poisoned flag rate 0.017 vs logged 0.483,
  [`efficiency_results.md`](docs/efficiency_results.md)).
- The Krum/Multi-Krum/trimmed-mean baselines, the Phase 4 rolling-history
  matrix and gradual-mode attacks are n=1 (seed 42) by design.
- Whether the detectors' failures are general, or entangled with this
  project's worst-case attacker-selection rule (which selects on the same
  compositional axis the detectors react to), is still open.
- No live run was done in which ByzAgent's decisions drive aggregation,
  because any number it produced would inherit the compositional confound.

**Engineering**

- The pipeline is Windows-oriented: checkpoint manifests such as
  `results/inspection/best_rounds_manifest.json` store Windows backslash
  paths.
- The pinned environment was tested on Windows only.
- A fresh clone has no processed data (`*.parquet` is git-ignored), so the
  backend only starts after the data pipeline has been run locally.

## Reproduce it

All commands run from the repo root in PowerShell unless noted. Everything
was developed and run on Windows 11 with an RTX 4050 (6 GB VRAM, a hard
ceiling that shaped several choices) and 24 GB RAM. Full runs are long: the
SHAP pipeline alone is about 3.7 hours for all 9 configurations.

What ran where: the GPU trained the centralized MLP (baselines and pilots)
and XGBoost, and ran the Ollama model behind ByzAgent. Federated training ran
on CPU: Flower installs its own isolated environment with torch 2.13.0+cpu
(verified in the two August environments and in every run made on
2026-10-12/13). SHAP, the dashboard backend and hot-swap retraining also run
on CPU.

### 1. Environment

The project used a conda env named `xfed` with Python 3.11. Use PowerShell:
on the development machine `conda activate` is a silent no-op in `cmd.exe`.

Create the environment from the repo root:

```powershell
conda env create -f environment.yml
conda activate xfed
```

[`environment.yml`](environment.yml) installs Python 3.11 and the pinned
packages in [`requirements.txt`](requirements.txt), including the CUDA 12.4
build of PyTorch 2.6.0. Key versions: flwr 1.33.0, torch 2.6.0, shap 0.51.0,
scikit-learn 1.9.0, xgboost 3.2.0, optuna 4.9.0, fastapi 0.138.2, uvicorn
0.49.0, streamlit 1.61.1, pandas 3.0.3, pyarrow 24.0.0, onnxruntime 1.31.0
(added 2026-10-13, after the fresh-env test below). Node.js 24 is needed
for `site/`, `frontend/` and `film/`.

This install was tested in a fresh conda env on the development machine
(Windows 11): `pip check` was clean and the Flower app, backend and data
scripts imported. NumPy and pandas come from pip there rather than conda's
MKL build, so low-level numerics may differ slightly from the original env.

Environment tested on Windows + NVIDIA (cu124 wheels); Linux/macOS need the matching torch index.

Flower reads its simulation settings from your user-level Flower config
(`%USERPROFILE%\.flwr\config.toml`), not from this repo. Copy the
`[superlink.local-simulation]` block from
[`federated/flwr_config.example.toml`](federated/flwr_config.example.toml)
into that file. The example requests one GPU per client, which makes the
simulation run one client at a time. Training itself runs on CPU (Flower's
isolated environment installs the CPU build of torch), so in practice this
setting only serializes the clients. Also set
`$env:PYTHONIOENCODING = "utf-8"` in the shell; otherwise Flower's summary
output crashes on the default Windows code page.

Paths are relative to the repo root. The raw dataset is expected in a
`Dataset` folder next to the repo (`../Dataset`, set by `paths.raw_dir` in
`configs/data.yaml`); set the `XFED_DATASET_DIR` environment variable to
put it anywhere else. The Flower app finds the repo root on its own;
`XFED_PROJECT_ROOT` overrides that if it ever guesses wrong.

### 2. Dataset

This project uses **Distrinet CICIDS2017 V4**, the IEEE CNS 2022 update of
CICIDS2017, published on Kaggle as
[`dhoogla/distrinetcicids2017`](https://www.kaggle.com/datasets/dhoogla/distrinetcicids2017),
version 4 (five per-day CSVs, about 1.15 GB). The dataset is not owned or
redistributed by this project; get it from its authors and cite both papers:

- L. Liu, G. Engelen, T. Lynar, D. Essam and W. Joosen, "Error Prevalence in
  NIDS datasets: A Case Study on CIC-IDS-2017 and CSE-CIC-IDS-2018," IEEE
  Conference on Communications and Network Security (CNS), 2022, pp. 254–262.
- G. Engelen, V. Rimmer and W. Joosen, "Troubleshooting an Intrusion
  Detection Dataset: the CICIDS2017 Case Study," IEEE Security and Privacy
  Workshops (SPW), Workshop on Traffic Measurements for Cybersecurity
  (WTMC), 2021.

Put the CSVs outside the repo, in a `Dataset` folder next to it (the project
used `C:\Pilli\Capstone\Dataset\`), or point `XFED_DATASET_DIR` at the folder. Derived data
(`*.parquet`, the demo `.npz` files) is git-ignored and not committed.

### 3. Cleaning, split and partitioning

```powershell
python src/data/clean.py           # raw CSVs -> clean.parquet
python src/data/families.py        # -> train_pool.parquet, test_global.parquet
python src/data/partition.py       # -> data/processed/partitions/ + manifest.json
python scripts/check_partitions.py --partition-dir data/processed/partitions
python scripts/make_val_split.py   # group-aware validation mask inside train_pool
python scripts/export_class_weights.py   # run once, before any Flower run
```

`partition.py` writes row-to-silo assignments for all 9 (α, seed)
configurations and a manifest holding the SHA256 of each assignment array.
`load_silo()` in `src/data/partition.py` recomputes that hash every time a
silo is loaded and raises on a mismatch, so a silently regenerated partition
cannot be trained on. `check_partitions.py` is a pre-flight check for silos
that would crash a federated round (empty train or test shards, missing
classes).

### 4. Training

Centralized and XGBoost baselines, one run per seed, then aggregated:

```powershell
python -m src.train.centralized --tag baseline_s42 --seed 42
python -m src.train.xgboost_baseline --tag xgb_s42 --seed 42
python scripts/aggregate_seeds.py --pattern "baseline_s*" --label centralized
python scripts/aggregate_seeds.py --results-dir results/xgboost --pattern "xgb_s*" --label xgboost
```

Repeat the first two lines for seeds 1337 and 2024 before aggregating.

Federated training uses the Flower app in `federated/`. Use exactly this
invocation. A bare `flwr run` from the repo root fails on purpose: the root
`pyproject.toml` has no Flower app section, so nothing can train against the
unused prototype in `src/federated/` by accident.

```powershell
flwr run federated local-simulation --run-config "alpha='0.5' seed=42" --stream
```

Each run trains for 20 rounds with 3 local epochs, writes to
`results/federated/<tag>/`, and keeps the best-by-validation round. The full
9-configuration sweep and the FedProx (μ=0.0005) sweep are scripted:

```powershell
powershell -ExecutionPolicy Bypass -File tools\run_sweep.ps1
powershell -ExecutionPolicy Bypass -File tools\run_sweep_fedprox.ps1
python scripts/aggregate_federated.py
```

Legacy client-side evaluation, which scores each silo on its own test rows
every round, is off by default (`legacy-client-test-eval = false` in
`federated/pyproject.toml`); training is the same either way. The published
runs were made with it on. To reproduce their `silo_metrics.jsonl` evaluate
rows, pass `-LegacyClientTestEval` to either sweep script, or
`--run-config "legacy-client-test-eval=true"` to `flwr run`.

### 5. Explanation check (SHAP export and agreement)

```powershell
python tools/extract_best_rounds.py         # -> results/inspection/best_rounds_manifest.json
python tools/local_shap_pipeline.py --all   # per-silo + global SHAP, all 9 configs
python tools/agreement_metrics.py           # Jaccard@10 and weighted tau
python tools/centralized_shap_floor.py      # seed-noise instability floor
python tools/round_wise_shap.py             # rounds 5/10/15/20, nsamples=1000
python tools/round_wise_agreement.py
python tools/parity_monitor.py --all        # multi-draw drift flags (long)
```

SHAP runs on CPU, which was measured to be faster than the GPU for this
small model. The FedProx variants take `--tag-prefix fedprox_mu0.0005` plus
a matching manifest path; see each script's docstring.

### 6. Trust check (ByzAgent)

Attacks, defenses and the agent are switched on through
`configs/attack.yaml`, `configs/defense.yaml` and `configs/agent.yaml`. In
their committed state all three leave plain FedAvg untouched.

1. **Poisoned run.** Set `attack.enabled: true` in `configs/attack.yaml`
   (locked primary: `f: 3`, `malicious_silos: [0, 3, 5]`, `mode: sudden`,
   `flip_fraction: 0.40`), then run the same `flwr run federated
   local-simulation` command at α=0.5, seed 42. Poisoned runs get their own
   result directory. The server-side test pass is blocked for poisoned
   runs; legacy client-side per-round test scores were still logged and are
   unused.
2. **Behaviour statistics.** Runs that predate the statistics logger are
   replayed, then checked with the Phase 1 gate:
   ```powershell
   python scripts/replay_client_stats.py --run-dir results/federated/fedavg_a0.5_s42
   python scripts/phase1_verification_gate.py
   ```
3. **Classical baselines.** Set `defense.strategy` to `multikrum`, `krum` or
   `trimmed_mean` in `configs/defense.yaml`, with `num_malicious_nodes` set
   to the true `f` (the oracle), and re-run training. Analyse with
   `scripts/phase2_analysis.py` (its arguments are listed in the script).
4. **ByzAgent.** Install [Ollama](https://ollama.com), pull the model, and
   keep Ollama serving on `http://localhost:11434` (the host set in
   `configs/agent.yaml`):
   ```powershell
   ollama pull llama3.1:8b-instruct-q4_K_M
   python scripts/phase3_verification_gate.py   # replays client_stats.jsonl through the agent
   python scripts/phase3_analysis.py
   python scripts/phase4_verification_gate.py   # current-round vs rolling-history matrix
   python scripts/phase4_analysis.py
   python scripts/phase_multiseed_agent_replay.py
   python scripts/phase_multiseed_fidelity_audit.py
   ```
   The reported agent numbers come from these retrospective replays over
   logged statistics, not from retraining. The agent samples at temperature
   0.2, so a fresh replay is a new sample and will not match the published
   decisions exactly. `phase3_verification_gate.py` overwrites
   `results/federated/<tag>/agent_decisions.jsonl`, the files the published
   Phase 3 numbers were computed from; back them up first.
   `defense.strategy: byzagent` wires the agent into live aggregation, but
   no reported number comes from a live ByzAgent run.

### 7. Dashboard (FastAPI + React)

The backend needs the processed data from step 3, the trained
`fedavg_a0.5_s42` checkpoint and `best_rounds_manifest.json`. At startup it
re-checks the served model's validation macro-F1 against the logged value;
it never reads the test set.

The two demo SHAP files are not redistributed. Rebuild them once. Each
script is a one-time, logged read of already-explained rows of
`test_global.parquet` (14 and 500 rows) for display only; see the test-set
access note in
[`docs/contribution_a_results.md`](docs/contribution_a_results.md#test-set-access-note).

```powershell
python -m tools.build_shap_eval_sidecar --tag fedavg_a0.5_s42
python -m tools.build_shap_streamed_pool --tag fedavg_a0.5_s42
```

Both files were committed at one point and later removed from tracking; they
remain in git history (`eval_rows_sidecar.npz` since `0d9a8aa`,
`streamed_pool.npz` since `2823faf`), so a full clone still fetches those old
copies. History was not rewritten.

The demo's validation SHAP pool is also rebuilt locally (about 45 minutes on
CPU). It reads only `train_pool.parquet` and `val_mask.parquet`, never the
test set. It explains 500 seeded validation rows covering all 9 families,
with the same explainer, background and checkpoint as the streamed pool
([`configs/val_shap_pool.yaml`](configs/val_shap_pool.yaml)). Its class
counts and additivity residuals are written to the tracked
`results/shap/fedavg_a0.5_s42/val_pool_summary.json`.

```powershell
python -m tools.build_shap_val_pool
```

The one-sentence LLM summaries (length not enforced) are committed in
`results/explanations/fedavg_a0.5_s42/sentences.json`;
`python -m tools.build_explanations --tag fedavg_a0.5_s42` regenerates them
with Ollama. The validation pool's sentences are committed in
`results/explanations/fedavg_a0.5_s42/val_sentences.json`, which also records
the model tag and digest, temperature, seed and prompt hash. They were made
with the same model and prompt, and took 35 minutes on the RTX 4050:

```powershell
python -m tools.build_explanations --tag fedavg_a0.5_s42 --pool val --seed 6006
```

The backend serves the model through ONNX Runtime fp32 by default
(`serving.engine` in [`configs/efficiency.yaml`](configs/efficiency.yaml);
set it to `torch` for the original path). At startup it refuses to serve
unless the ONNX predictions equal PyTorch's on every validation row.

Then, in three terminals:

```powershell
uvicorn backend.main:app --reload
```

```powershell
python -m backend.simulator
```

```powershell
cd frontend
npm ci
npm run dev
```

The API listens on `http://127.0.0.1:8000`, and the Vite dev server proxies
`/api` to it. The simulator is optional: it replays rows so the alert
stream moves. The dashboard simulator replays validation rows as display traffic and marks each alert against its true label; no aggregate metric is computed and nothing is selected from it. The public site's replay uses the 500 stored test-row outputs documented above.
By default (`simulator.source_split: val_shap_pool` in
`configs/backend.yaml`) it replays the 500 rows of the validation SHAP pool in
stored order, so every alert has a SHAP panel and an LLM-generated summary. Set `source_split: val` to replay the whole
validation split instead; those alerts have no SHAP.
To replay test rows instead, set `simulator.source_split: test`; the
simulator refuses unless the served checkpoint's
hash is listed in `simulator.test_split_checkpoint_allowlist` (empty by
default).

The older Streamlit dashboard still runs with `streamlit run app.py`.
